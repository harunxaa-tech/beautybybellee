# Soft-deleted record protection
Applied DB migration prevent_business_record_resurrection on 2026-11-25. BEFORE UPDATE trigger on customers, catalog_items, offers, jobs, events, tasks and invoices; rejects clearing existing deleted_at, including ON CONFLICT DO UPDATE from stale snapshots. SECURITY INVOKER, fixed search path and revoked direct client execution. Normal update and soft delete still permitted. Verified all seven triggers enabled. Sequential rollback-only real customers table test passed: create, update, delete, attempted direct resurrection and attempted stale upsert both rejected with SYNC_DELETED_RECORD_CONFLICT; original deletion and name preserved; synthetic row rolled back. No other table integration test or simultaneous connection test performed. No existing data deleted or restored.
Branch client translates explicit DB conflict to actionable German error, preserves existing pending state on failure; no automatic retry override. Existing full snapshot architecture still allows other concurrent updates to overwrite live rows; no CAS yet. This guard does not prevent resurrection after physical deletion, edits of already-deleted rows that retain marker, or new rows with different IDs. Intentional restoration via clearing deleted_at is now blocked and requires a separate audited recovery design. Existing partial writes before conflict may have committed. No production frontend release.
